# SchoolFix

Заявки на ремонт и проблемы в школе. React + TypeScript + Vite + Tailwind, бэкенд — Supabase
(Postgres, Auth, RLS, RPC, Storage).

## Запуск с нуля

1. **Supabase**: создайте проект → *SQL Editor* → вставьте `supabase/schema.sql` **целиком** → Run.
   Скрипт идемпотентный, его можно запускать повторно.
2. **Auth**: *Authentication → Providers → Email* включён. Для локальной разработки можно отключить
   «Confirm email», в проде — оставить и указать *Site URL* (адрес деплоя) в *Authentication → URL Configuration*.
3. **Ключи**: `cp .env.example .env`, впишите `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`
   (*Project Settings → API*). Service-role ключ во фронт **не кладём никогда**.
4. `npm install && npm run dev`.
5. **Первый super_admin**: зарегистрируйтесь в приложении, затем один раз в SQL Editor:
   ```sql
   update public.profiles set role = 'super_admin' where email = 'you@school.kz';
   ```
6. Дальше всё через интерфейс: *Управление → Инвайт-коды* → создать код → передать учителю/сотруднику →
   он вводит код в *Профиль* → вы подтверждаете в *Управление → Заявки на роли*.

## Деплой

`npm run build` → папка `dist/`. Vercel/Netlify: задайте те же две переменные окружения.
SPA-fallback уже лежит в `vercel.json` и `public/_redirects`. Любой другой хостинг — настройте
перенаправление всех путей на `index.html`.

## Как устроена безопасность

| Что | Где обеспечивается |
|---|---|
| Роль нельзя изменить прямым запросом | у `authenticated` нет UPDATE на `profiles`; роль меняют только RPC `admin_review_role_request` / `admin_set_user_role` |
| Роль не берётся из регистрационных данных | триггер `handle_new_user` всегда создаёт `student` |
| Ученик/учитель видит только свои заявки | RLS `issues_select` |
| Ученик не может поставить статус | column-level GRANT: на `issues` клиент может вставлять только `title, description, category, location, photo_path`, обновлять только `status`; UPDATE-политика — только triage |
| Коды | в БД лежит sha256; `code_hash` закрыт от SELECT даже админу; открытый код возвращается один раз |
| Отключённый пользователь | `app_role()` возвращает null → ни одна политика его не пропускает |
| Фото | приватный бакет, путь `<uid>/<file>`, просмотр — автор и triage, ссылки подписанные |

Кнопки, скрытые во фронте (`isAdmin`, `isTriage`), — только UX. Всё проверяется в Postgres.

## Структура

```
supabase/schema.sql        типы, таблицы, RLS, RPC, Storage, Realtime, GRANT/REVOKE
src/lib/api.ts             ЕДИНСТВЕННОЕ место вызовов supabase.from/rpc/storage (try/catch + toast)
src/lib/auth.tsx           сессия + профиль, живое обновление роли
src/lib/errors.ts          Postgres/RPC/сеть → понятный текст
src/lib/useLive.ts         Realtime-подписка «перечитать при изменении»
src/pages/*                вход, список заявок, новая заявка, заявка, профиль, админка
src/pages/admin/*          заявки на роли, пользователи, инвайт-коды
```

## Сознательные упрощения MVP

- Нет редактирования/удаления заявок и комментариев (в БД нет политик на это).
- Нет смены имени/пароля/почты в профиле, нет сброса пароля.
- Нет пагинации и поиска по заявкам (фильтр только по статусу). Ок до нескольких тысяч заявок.
- Нет уведомлений на почту/в Telegram о новых заявках и смене статуса.
- Нет журнала аудита (кто и когда менял роли/статусы, кроме `reviewed_by` у заявок на роли).
- Нет защиты от перебора инвайт-кодов (rate limit). Код — 64 бита случайности + срок жизни, но лимита попыток нет.
- Нет сжатия фото на клиенте, один файл на заявку.
- Админ (не только staff) может менять статусы и комментировать любые заявки — в ТЗ это не прописано, решение принято сознательно.
- Ученик и учитель могут комментировать свои заявки (ТЗ говорит только про комментарии staff).
- `photo_url` из ТЗ называется `photo_path`: хранится путь в бакете, подписанную ссылку клиент запрашивает сам.
- Realtime — «перечитать при событии». Если WebSocket отвалился, данные обновятся при следующем действии/перезагрузке.
- Автотестов на фронте нет; RLS/RPC проверены SQL-сценарием (см. CHECKLIST.md).
